# 01 — TallyLedger Schema Restructuring & Direct-Twin Architecture

## 1. Why Refactor Now (Testing Phase Advantage)

TallyLedger's initial `types.ts` and database schema were modeled around a **corporate furniture/equipment asset tracker** (`unitCost` only, rigid equipment categories, warehouse `location`, and basic `Completed | Pending | Refunded` order states).

Refactoring during the testing phase prevents breaking bugs when running a **Philippine Sari-Sari Store** and its direct retail twins:

- **Small Hardware & Construction Supply (*Tindahan ng Hardware*)**
- **Agrivet & Poultry Supply Stores**
- **Neighborhood Bakeries (*Panaderya*)**
- **School & Office Supply Stalls**

---

## 2. Core Structural Gaps Solved by Restructuring

| Domain Area | Legacy Equipment Model (`types.ts`) | Restructured Retail-Twin Model |
| :--- | :--- | :--- |
| **Retail Pricing** | Stores `unitCost` only; no selling price (`unitPrice` / SRP) on products. | Stores both `cost_price` and `default_unit_price` (SRP) plus `unit_cost_snapshot` on every sale for true profit margins. |
| **Bulk-to-*Tingi* Math** | Plain integer `quantity`; no unit conversions. | Adds `base_unit` (`pc`, `kg`, `meter`, `sack`, `tasa`), `parent_product_id`, and `conversion_factor` for repacking 50kg sacks or boxes into *tingi*. |
| **Unbarcoded / Missing SKUs** | Assumes every item has a pre-assigned SKU. | Supports real barcodes (`480...`) alongside deterministic synthetic SKUs (`GEN-<STORE>-<SLUG>`) and `aliases_json`. |
| **Informal Credit (*Utang*)** | No customer ledger, partial payments, or credit balances. | Dedicated `customers` ledger + `credit_payments` table + `amount_paid` and `status` (`UTANG`, `PARTIAL`, `FOR_DELIVERY`). |
| **Multi-Store & Archives** | Single-tenant; importing old sales deducts live stock. | Adds `store_id` isolation (RLS), `record_source` (`POS_LIVE` vs. `NOTEBOOK_ARCHIVE`), and `deduct_stock` boolean protection. |

---

## 3. Three-Layer Hybrid Architecture (Database + UI)

Instead of maintaining separate codebases per store type, TallyLedger uses one unified database schema paired with store-level configuration toggles (`store_config`):

1. **Superset Core Columns (Approach A):** Standard retail columns (`customer_id`, `customer_name`, `status`, `amount_paid`) are built directly into `sales` as nullable or defaulted fields.
   - *Fast Counter Stores (Sari-Sari / Bakery / School Supplies):* Hide `customer_name` and `status` on the UI; the app silently writes `NULL` and `'COMPLETED'`.
   - *Credit-Heavy Stores (Hardware / Agrivet):* Enable `require_customer_name = 1` and `require_status = 1` to log contractor/farmer credit tabs.
2. **Dynamic JSON Bucket (Approach B):** `extra_metadata` (`TEXT` in SQLite / `JSONB` in Postgres) absorbs vertical-specific fields, such as `{"rider": "Kuya Ben"}`, `{"harvest_due": "2026-12-15"}`, or `{"batch_no": "B102"}`, without schema migrations.
3. **CSV & Notebook Staging Adapter (Approach C):** External spreadsheets and digitized notebook logs (e.g., Sept–Nov 2023 records) pass through a saved `column_mapping_json` profile, generate synthetic SKUs for missing barcodes, and set `deduct_stock = 0` so historical revenue never corrupts 2026 physical shelf counts.

## 4. Refactored `types.ts` Contract

```typescript
export type BusinessType = 'SARI_SARI' | 'HARDWARE' | 'AGRIVET' | 'BAKERY' | 'SCHOOL_SUPPLY';
export type UnitType = 'pc' | 'pack' | 'kg' | 'g' | 'meter' | 'liter' | 'sack' | 'box' | 'sheet' | 'tasa';
export type SaleStatus = 'Completed' | 'Utang' | 'Partial' | 'For Delivery' | 'Voided' | 'Refunded';
export type RecordSource = 'POS_LIVE' | 'CSV_IMPORT' | 'NOTEBOOK_ARCHIVE';

export interface WorkspaceSettings {
  storeId: string;
  businessType: BusinessType;
  storeName: string;
  currency: 'PHP' | 'USD';
  requireCustomerName: boolean;
  requireSaleStatus: boolean;
  enableUnitConversions: boolean;
  columnMapping?: Record<string, string>;
}

export interface InventoryItem {
  id: string;
  storeId: string;
  sku: string;
  name: string;
  aliases?: string[];
  category: string;
  baseUnit: UnitType;
  parentProductId?: string;
  conversionFactor: number;
  location?: string;
  supplier?: string;
  quantity: number;
  reorderPoint: number;
  unitCost: number;
  unitPrice: number;
  isAutoGeneratedSku: boolean;
  isActive: boolean;
  lastUpdated: string;
  syncedAt?: string;
}

export interface CustomerRecord {
  id: string;
  storeId: string;
  fullName: string;
  phoneNumber?: string;
  customerType: 'SUKI' | 'CONTRACTOR' | 'FARMER' | 'RESELLER' | 'WALK_IN';
  creditLimit: number;
  currentBalance: number;
  notes?: string;
  updatedAt: string;
}

export interface SaleRecord {
  id: string;
  receiptGroupId?: string;
  storeId: string;
  orderNumber: string;
  customerId?: string;
  customerName?: string;
  channel: 'POS Counter' | 'Walk-In' | 'Wholesale' | 'Delivery' | 'Notebook Archive';
  inventoryItemId?: string;
  itemName: string;
  sku: string;
  unitSold: UnitType;
  quantity: number;
  unitPrice: number;
  unitCostSnapshot?: number;
  totalAmount: number;
  amountPaid: number;
  status: SaleStatus;
  recordSource: RecordSource;
  deductStock: boolean;
  extraMetadata?: Record<string, unknown>;
  date: string;
  notes?: string;
  syncedAt?: string;
}
```
