````
# 01 — TallyLedger Schema Restructuring & Direct-Twin Architecture

## 1. Why Refactor Now (Testing Phase Advantage)
TallyLedger's initial `types.ts` and database schema were modeled around a **corporate furniture/equipment asset tracker** (`unitCost` only, rigid equipment categories, warehouse `location`, and basic `Completed | Pending | Refunded` order states)[cite: 1]. 

Refactoring during the testing phase prevents breaking bugs when running a **Philippine Sari-Sari Store** and its direct retail twins:
* **Small Hardware & Construction Supply (*Tindahan ng Hardware*)**
* **Agrivet & Poultry Supply Stores**
* **Neighborhood Bakeries (*Panaderya*)**
* **School & Office Supply Stalls**

---

## 2. Core Structural Gaps Solved by Restructuring

| Domain Area | Legacy Equipment Model (`types.ts`) | Restructured Retail-Twin Model |
| :--- | :--- | :--- |
| **Retail Pricing** | Stores `unitCost` only; no selling price (`unitPrice` / SRP) on products[cite: 1]. | Stores both `cost_price` and `default_unit_price` (SRP) plus `unit_cost_snapshot` on every sale for true profit margins. |
| **Bulk-to-*Tingi* Math** | Plain integer `quantity`; no unit conversions[cite: 1]. | Adds `base_unit` (`pc`, `kg`, `meter`, `sack`, `tasa`), `parent_product_id`, and `conversion_factor` for repacking 50kg sacks or boxes into *tingi*. |
| **Unbarcoded / Missing SKUs** | Assumes every item has a pre-assigned SKU[cite: 1]. | Supports real barcodes (`480...`) alongside deterministic synthetic SKUs (`GEN-<STORE>-<SLUG>`) and `aliases_json`[cite: 2]. |
| **Informal Credit (*Utang*)** | No customer ledger, partial payments, or credit balances[cite: 1]. | Dedicated `customers` ledger + `credit_payments` table + `amount_paid` and `status` (`UTANG`, `PARTIAL`, `FOR_DELIVERY`). |
| **Multi-Store & Archives** | Single-tenant; importing old sales deducts live stock[cite: 1]. | Adds `store_id` isolation (RLS), `record_source` (`POS_LIVE` vs. `NOTEBOOK_ARCHIVE`), and `deduct_stock` boolean protection[cite: 2, 5]. |

---

## 3. Three-Layer Hybrid Architecture (Database + UI)
Instead of maintaining separate codebases per store type, TallyLedger uses one unified database schema paired with store-level configuration toggles (`store_config`)[cite: 2]:

1. **Superset Core Columns (Approach A):** Standard retail columns (`customer_id`, `customer_name`, `status`, `amount_paid`) are built directly into `sales` as nullable or defaulted fields[cite: 2].
   * *Fast Counter Stores (Sari-Sari / Bakery / School Supplies):* Hide `customer_name` and `status` on the UI; the app silently writes `NULL` and `'COMPLETED'`[cite: 2].
   * *Credit-Heavy Stores (Hardware / Agrivet):* Enable `require_customer_name = 1` and `require_status = 1` to log contractor/farmer credit tabs[cite: 2].
2. **Dynamic JSON Bucket (Approach B):** `extra_metadata` (`TEXT` in SQLite / `JSONB` in Postgres) absorbs vertical-specific fields—such as `{"rider": "Kuya Ben"}`, `{"harvest_due": "2026-12-15"}`, or `{"batch_no": "B102"}`—without schema migrations[cite: 2].
3. **CSV & Notebook Staging Adapter (Approach C):** External spreadsheets and digitized notebook logs (e.g., Sept–Nov 2023 records) pass through a saved `column_mapping_json` profile, generate synthetic SKUs for missing barcodes, and set `deduct_stock = 0` so historical revenue never corrupts 2026 physical shelf counts[cite: 2, 5].
````

````
## 1. Local Edge Database (SQLite — WAL Mode)
Deploy this schema on the counter terminal (Electron / local backend or SQLite WASM OPFS). `WAL` mode and `busy_timeout` guarantee sub-5ms writes and zero corruption during sudden brownouts.

```sql

PRAGMA synchronous = NORMAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;

-- 1. Store Configuration & Vertical Feature Flags
CREATE TABLE store_config (
    store_id TEXT PRIMARY KEY,
    store_name TEXT NOT NULL,
    business_type TEXT NOT NULL DEFAULT 'SARI_SARI',  -- 'SARI_SARI', 'HARDWARE', 'AGRIVET', 'BAKERY', 'SCHOOL_SUPPLY'
    require_customer_name INTEGER NOT NULL DEFAULT 0,
    require_status INTEGER NOT NULL DEFAULT 0,

    canonical_name TEXT NOT NULL,
    category TEXT,
    aliases_json TEXT DEFAULT '[]',

    base_unit TEXT NOT NULL DEFAULT 'pc',             -- 'pc', 'kg', 'g', 'pack', 'meter', 'liter', 'sack', 'box', 'sheet', 'tasa'
    parent_product_id TEXT REFERENCES products(product_id),
    conversion_factor REAL NOT NULL DEFAULT 1.0,
    
    -- Stock & Pricing
    location TEXT,
    supplier TEXT,
    stock_qty REAL NOT NULL DEFAULT 0,
    low_stock_threshold REAL NOT NULL DEFAULT 5,
    cost_price REAL NOT NULL DEFAULT 0,
    default_unit_price REAL NOT NULL DEFAULT 0,
    
    is_auto_generated_sku INTEGER NOT NULL DEFAULT 0,
    is_active INTEGER NOT NULL DEFAULT 1,
    updated_at TEXT NOT NULL DEFAULT (datetime('now')),
    UNIQUE(store_id, sku)

-- 3. Customer & Suki Credit Ledger (Utang / Contractor / Farmer Tabs)
CREATE TABLE customers (
    customer_id TEXT PRIMARY KEY,
    store_id TEXT NOT NULL REFERENCES store_config(store_id) ON DELETE CASCADE,
    full_name TEXT NOT NULL,
    phone_number TEXT,
    customer_type TEXT NOT NULL DEFAULT 'SUKI',
    credit_limit REAL NOT NULL DEFAULT 0,
    current_balance REAL NOT NULL DEFAULT 0,
    notes TEXT,
    updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

-- 4. Unified Sales Ledger (Live POS + Historical Notebook Archives)
CREATE TABLE sales (
    sale_id TEXT PRIMARY KEY,                         -- UUIDv7 or ULID
    receipt_group_id TEXT,
    store_id TEXT NOT NULL REFERENCES store_config(store_id) ON DELETE CASCADE,
    product_id TEXT REFERENCES products(product_id),
    sku TEXT NOT NULL,
    product_name TEXT NOT NULL,
    unit_sold TEXT NOT NULL DEFAULT 'pc',
    quantity REAL NOT NULL,
    unit_price REAL NOT NULL,
    unit_cost_snapshot REAL DEFAULT 0,
    total_amount REAL GENERATED ALWAYS AS (quantity * unit_price) STORED,
    
    -- Credit & Fulfillment
    customer_id TEXT REFERENCES customers(customer_id),
    customer_name TEXT,
    status TEXT NOT NULL DEFAULT 'COMPLETED',         -- 'COMPLETED', 'UTANG', 'PARTIAL', 'FOR_DELIVERY', 'VOIDED'
    amount_paid REAL NOT NULL DEFAULT 0,
    
    -- Archive & Sync Control
    record_source TEXT NOT NULL DEFAULT 'POS_LIVE',   -- 'POS_LIVE', 'CSV_IMPORT', 'NOTEBOOK_ARCHIVE'

    extra_metadata TEXT DEFAULT '{}',
    sold_at TEXT NOT NULL,
    synced_at TEXT
);

    payment_id TEXT PRIMARY KEY,
    store_id TEXT NOT NULL REFERENCES store_config(store_id) ON DELETE CASCADE,
    customer_id TEXT NOT NULL REFERENCES customers(customer_id),
    sale_id TEXT REFERENCES sales(sale_id),
    amount_paid REAL NOT NULL,
    payment_method TEXT NOT NULL DEFAULT 'CASH',      -- 'CASH', 'GCASH', 'MAYA', 'BANK'
    notes TEXT,
    paid_at TEXT NOT NULL DEFAULT (datetime('now')),
    synced_at TEXT
);

-- 6. Local-First Sync Outbox (Counter -> Laptop Hub -> Supabase)
CREATE TABLE sync_outbox (
    outbox_id INTEGER PRIMARY KEY AUTOINCREMENT,
    table_name TEXT NOT NULL,
    record_id TEXT NOT NULL,
    operation TEXT NOT NULL,                          -- 'INSERT', 'UPDATE', 'DELETE'
    payload_json TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    synced_at TEXT
);

-- Indexes
CREATE INDEX idx_products_store_name ON products(store_id, canonical_name);
CREATE INDEX idx_sales_store_date ON sales(store_id, sold_at);
CREATE INDEX idx_sales_store_sku ON sales(store_id, sku);
CREATE INDEX idx_sales_status ON sales(store_id, status);
CREATE INDEX idx_customers_store ON customers(store_id, full_name);
CREATE INDEX idx_outbox_unsynced ON sync_outbox(synced_at) WHERE synced_at IS NULL;
````

## 3. Atomic Transactions (Checkout & Break-Pack)

SQL

```
-- A. Break-Pack Conversion (e.g., Opening 1 x 50kg Sack into 50 x 1kg Repacks)
BEGIN TRANSACTION;
UPDATE products SET stock_qty = stock_qty - 1, updated_at = datetime('now')
WHERE product_id = :parent_sack_id;

UPDATE products SET stock_qty = stock_qty + :conversion_factor, updated_at = datetime('now')
WHERE product_id = :child_repack_id;
COMMIT;

-- B. Live POS Checkout with Optional Utang Balance Update
BEGIN TRANSACTION;
INSERT INTO sales (sale_id, store_id, product_id, sku, product_name, unit_sold, quantity, unit_price, customer_id, status, amount_paid, deduct_stock, sold_at)
VALUES (:sale_id, :store_id, :product_id, :sku, :product_name, :unit_sold, :qty, :price, :customer_id, :status, :amount_paid, 1, datetime('now'));

UPDATE products SET stock_qty = stock_qty - :qty, updated_at = datetime('now')
WHERE product_id = :product_id;

-- If status is 'UTANG' or 'PARTIAL', increment customer's running balance
UPDATE customers SET current_balance = current_balance + ((:qty * :price) - :amount_paid), updated_at = datetime('now')
WHERE customer_id = :customer_id AND :status IN ('UTANG', 'PARTIAL');
COMMIT;
```

````
# 03 — Testing-Phase Migration & 3-Tier Backup Playbook

## 1. Clean Reset & Migration Steps (Testing -> Retail-Twin Schema)
Because TallyLedger is still in testing without live production ledger locks, execute a clean reset so legacy equipment columns do not linger:

1. **Export Any Useful Test Items:** Dump existing test products to CSV if needed (`sku, name, unitCost`).
2. **Reset Local Counter SQLite:**
   * Close the app/worker so no `-wal` or `-shm` locks remain.
   * Rename the old file (`tallyledger_legacy_test.db.bak`) and initialize a fresh `tallyledger.db` using `02_drop_in_database_template.md`.
   * Seed `store_config` with your store's `store_id` (e.g., `STORE_ILIGAN_01`) and `business_type = 'SARI_SARI'`.
3. **Reset Supabase Test Tables:**
   * In Supabase SQL Editor, drop the old equipment test tables (`DROP TABLE IF EXISTS ... CASCADE;`) and run the PostgreSQL DDL from `02_drop_in_database_template.md`.
   * Insert your matching `store_config` row linked to your `auth.uid()`.
4. **Update Data-Access Layer:**
   * Map snake_case DB columns (`unit_price`, `base_unit`, `deduct_stock`) to camelCase `types.ts` fields (`unitPrice`, `baseUnit`, `deductStock`).
   * Ensure every `INSERT`/`UPDATE` writes a JSON payload to `sync_outbox` inside the same SQLite transaction.

---

## 2. Historical Notebook Ingestion (Sept 25 – Nov 7, 2023 Backlog)
Your handwritten notebooks (`Date | Qty | Product | Sales`) contain ~1,920 to 3,840 entries per 80-leaf book (~20–38 MB per 10 books)[cite: 3, 5]. Import them without affecting live 2026 inventory[cite: 5]:

1. **Transcribe to 4-Column CSV:** `Date, Qty, Product, Sales`[cite: 5].
2. **Normalize During Import:**
   * Calculate `unit_price = Sales / Qty`[cite: 5].
   * Check `products` (`canonical_name` and `aliases_json`); if missing, auto-generate deterministic synthetic SKU `GEN-ST01-<SLUG>` with `is_auto_generated_sku = 1`[cite: 2, 5].
   * Set `record_source = 'NOTEBOOK_ARCHIVE'` and `deduct_stock = 0` so historical revenue builds 2023–2026 trend reports without subtracting from current shelf counts[cite: 5].
3. **Day-0 Physical Inventory Cutover:** Perform one physical count of current shelves, enter opening `stock_qty`, and switch `deduct_stock = 1` for all live POS sales[cite: 5].

## 3. 3-Tier Local-First Backup & Sustainability Architecture
This topology keeps checkout 100% offline-capable at the counter while eliminating single-drive hardware risk and staying well within Supabase's Free Tier (500 MB DB + 1 GB Storage) for decades.

```text
┌───────────────────────────┐
│ TIER 1: EDGE COUNTER PC   │  SQLite (WAL Mode) -> < 5 ms offline checkout
│ (Single Source of Truth)  │  Writes to local tables + `sync_outbox`
└─────────────┬─────────────┘
              │ (1) LAN Sync + Hourly `VACUUM INTO` Snapshot
              ▼
┌───────────────────────────┐
│ TIER 2: SELF-HOSTING      │  Receives hourly `.db` snapshots over SMB/LAN
│ LAPTOP (Future RAID1 NAS) │  Runs local Postgres + compresses weekly `.db.zst`
└─────────────┬─────────────┘
              │ (2) Background Relay (When Internet Available)
              ▼
┌───────────────────────────┐
│ TIER 3: SUPABASE CLOUD    │  • Postgres: `weekly_sales_summary` (~1 MB/yr)
│ (Off-Site Disaster Mirror)│  • Storage: `archive_YYYY_Www.db.zst` (~3 MB/yr)
└───────────────────────────┘
````

### Automated Backup Schedule

- **Hourly (Counter PC -> Self-Hosting Laptop):** Run SQLite's online backup command (safe while the counter is actively selling):
    
    Bash
    
    ```
    sqlite3 /data/tallyledger.db "VACUUM INTO '/mnt/laptop_backup/hourly/tally_$(date +%Y%m%d_%H).db';"
    ```
    
    _(Retain last 48 hourly files; delete older hourly files automatically)._
    
- **Weekly — Sunday 11:00 PM (Self-Hosting Laptop -> Supabase):**
    
    1. **Compress Full Database Snapshot:** Compress the latest clean SQLite snapshot using Zstandard (`zstd -19 tally_latest.db -o tally_2026_W48.db.zst`) — shrinks ~25 MB/year of raw rows down to **~2.5–4 MB/year** — and upload to a private `db-archives` bucket in **Supabase Storage** (1 GB free quota = 250+ years).
        
    2. **Upsert Weekly Roll-Up Row:** Push 1 summary row into Supabase Postgres `weekly_sales_summary` (< 1 MB/year = 400+ years inside the 500 MB database cap). This also prevents Supabase Free Tier from auto-pausing after 7 days of inactivity.
        

## 4. Disaster Recovery Playbook

- **Scenario A — Counter PC SSD Dies:** Buy/boot replacement PC -> copy latest `.db` snapshot from the Self-Hosting Laptop -> reopen POS in under 15 minutes.
    
- **Scenario B — Self-Hosting Laptop Fails (or Upgrading to Dual-Bay NAS):** Counter PC continues operating uninterrupted offline; point the hourly SMB target and outbox worker IP to the replacement laptop or RAID 1 NAS[cite: 3].
    
- **Scenario C — Total Local Loss (Flood / Fire / Theft):** Download latest `tally_YYYY_Www.db.zst` from Supabase Storage, decompress (`unzstd`), and restore the complete transaction history onto new hardware[cite: 3].
